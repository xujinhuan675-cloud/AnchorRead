# AnchorRead 部署与发布

## 架构总览

部署采用 **全自动 CI/CD**：构建发生在 GitHub 托管 runner，生产服务器只负责取镜像与蓝绿切换。

```
push 到 main（或手动 workflow_dispatch）
   │
   ▼  GitHub Actions（.github/workflows/deploy.yml）
   ├─ job build-push：构建 linux/amd64 镜像 → 推送 ghcr.io/xujinhuan675-cloud/anchorread:<sha>
   └─ job deploy：SSH 到服务器执行 scripts/remote-deploy.sh
                    → docker login ghcr.io → docker pull → 蓝绿切换 → 健康检查 → 失败自动回滚
```

**为什么这样设计**：旧流程在生产宿主机上执行 `docker build`（含 `next build --webpack` + Sentry sourcemap 上传），与其它常驻容器争抢 CPU/内存/IO，导致负载高、swap 抖动。迁移后生产机不再构建，只做轻量的 `docker pull` 与容器切换。

## 发布原则

提交、同步、部署是同一条发布链上三个可核对的节点：

1. **本地提交**：工作区必须干净，提交信息说明功能。
2. **Git 同步**：提交推送到 `origin/main`，确认远端哈希与本地一致。
3. **CI 部署**：GitHub Actions 构建同哈希镜像、推送 GHCR，服务器拉取该镜像并蓝绿切换，最后校验线上地址。

不要只凭「已经 push」判断线上已更新。线上版本必须以 **run 成功** 与 **健康检查结果** 为准。

## 一键发布

在仓库根目录运行 PowerShell 触发器（需本机已安装并认证 `gh` CLI）：

```powershell
.\scripts\deploy-server.ps1 -Push
```

`-Push` 会先把 `HEAD` 推到 `origin/main`（push 事件自动触发部署），再监控 run 直到结束，最后从本机校验线上地址。

**首次部署必须用 `-Push`**：`deploy.yml` 尚未进入默认分支时 `workflow_dispatch` 不可用，而 push 事件会用被推送提交里的 workflow 直接触发首次部署。

手动重新部署当前 `main`（远端已是最新、无新提交时）：

```powershell
.\scripts\deploy-server.ps1
```

此时脚本走 `workflow_dispatch` 触发。

默认配置：

- 工作流：`deploy.yml`
- 分支/ref：`main`
- 线上检查：`https://anchorread.flowguide.cc/`

## 触发器（deploy-server.ps1）做什么

1. 校验 `gh` CLI 已安装且已认证，并确认当前仓库。
2. `-Push` 时：拒绝未提交的工作区，推送 `HEAD` 到 `origin/<Ref>`。
3. 触发部署：push 事件（`-Push`）或 `workflow_dispatch`（默认，或 push 显示 up-to-date 时）。
4. 轮询识别本次新建的 run，并 `gh run watch --exit-status` 监控到结束。
5. 从本机请求线上 URL，附加提交短哈希避免复用旧缓存。

常用参数：

```powershell
.\scripts\deploy-server.ps1 -Ref main -SkipHealthCheck   # 只触发+监控，不做本机线上探测
```

## CI（deploy.yml）做什么

- **build-push**：`docker buildx` 构建 `linux/amd64` 镜像，注入 `NEXT_PUBLIC_SENTRY_*` 构建参数与 `sentry_env` secret，推送到 GHCR，标签为 `<full-sha>` 与 `latest`，并记录 `org.opencontainers.image.revision`。使用 GHA 缓存加速。
- **deploy**：checkout 后通过 SSH 以 `bash -s` 把 `scripts/remote-deploy.sh` 管道到服务器执行，传入镜像引用与提交号。
- **并发**：`concurrency: production-deploy` 且 `cancel-in-progress: false`，生产部署串行、不互相打断。

## 远端脚本（remote-deploy.sh）做什么

在服务器上执行，逻辑与旧的服务器端部署一致，只是把 `docker build` 换成 `docker pull`：

1. 从服务器本地 `.env` 读取 `GHCR_USER` / `GHCR_PAT` 登录 GHCR（凭证不经 CI 传递、不落日志）。
2. `docker pull` 目标镜像。
3. 组装运行时环境（旧容器环境 + 服务器 `.env`），并剥离 Sentry 构建凭证与 GHCR 拉取凭证，确保不进入运行容器。
4. 用临时端口（默认 `127.0.0.1:3002`）启动候选容器并做本机健康检查。
5. 通过后停旧容器、改名为 `anchorread-rollback-<short-commit>`，在 `127.0.0.1:3001` 启动新容器。
6. 新容器起不来或健康检查失败时，自动恢复回滚容器。

服务器默认参数：项目目录 `/opt/anchorread`、容器 `anchorread`、数据卷 `anchorread-data`、线上端口 `3001`、候选端口 `3002`。

## 需要配置的凭证

### GitHub Secrets（AnchorRead 仓库 → Settings → Secrets and variables → Actions）

| Secret | 用途 | 来源 |
| --- | --- | --- |
| `SENTRY_AUTH_TOKEN` | 构建期上传 sourcemap | 现服务器 `/opt/anchorread/.env` |
| `SENTRY_ORG` / `SENTRY_PROJECT` | 同上 | 同上 |
| `NEXT_PUBLIC_SENTRY_DSN` | 烤进浏览器 bundle | 同上 |
| `NEXT_PUBLIC_SENTRY_ENVIRONMENT` | 同上（默认 `production`） | 同上 |
| `NEXT_PUBLIC_SENTRY_TRACES_SAMPLE_RATE` | 同上（默认 `0.2`） | 同上 |
| `DEPLOY_SSH_HOST` | 服务器主机/IP | 本机 `~/.ssh/config` 中 `lcayun-1panel` 对应值 |
| `DEPLOY_SSH_PORT` | SSH 端口（默认 22） | 同上 |
| `DEPLOY_SSH_USER` | SSH 用户 | 同上 |
| `DEPLOY_SSH_KEY` | SSH 私钥（PEM 全文） | 可复用本机连该服务器的密钥对 |

> `GITHUB_TOKEN` 由 Actions 每次运行自动签发，工作流已声明 `permissions: packages: write`，**无需手动配置**即可推送 GHCR。

### 服务器端准备（`lcayun-1panel`）

1. 在 `/opt/anchorread/.env` 增加 GHCR 拉取凭证（`read:packages` 的账号级 PAT）：

   ```dotenv
   GHCR_USER=<你的 GitHub 用户名>
   GHCR_PAT=<read:packages 权限的 PAT>
   ```

2. 把 `DEPLOY_SSH_KEY` 对应的**公钥**加入服务器 `~/.ssh/authorized_keys`。
3. 确认服务器能访问 `ghcr.io`（网络可达）。
4. 运行时环境（`ANCHORREAD_API_KEY`、Supabase 等）继续保留在 `/opt/anchorread/.env`，逻辑不变。
5. 如果要启用图解请求的多实例路由，在同一个 `.env` 中配置共享 Redis，并让容器加入 Redis 所在 Docker 网络：

   ```dotenv
   ANCHORREAD_DIAGRAM_BROKER=redis
   ANCHORREAD_REDIS_URL=redis://redis:6379
   DOCKER_NETWORK=1panel-network
   # 多副本部署时每个副本必须唯一；不设置则由进程生成实例标识
   ANCHORREAD_INSTANCE_ID=anchorread-1
   ```

   `remote-deploy.sh` 会在 Redis 配置缺少 URL 时提前失败，并把 `DOCKER_NETWORK` 同时用于候选和线上容器。Redis 只应在内网监听，生产环境按实际服务名、TLS 和认证参数替换示例 URL。

> `.env` 只存在于服务器，不入库；`GHCR_*` 与 Sentry 构建凭证会在启动容器前被剥离，不会进入运行容器。

图解 broker 的运行时状态可通过 `/api/mcp/authorization` 查看：`requestBroker=redis` 与 `requestRoutingMultiInstance=true` 表示跨进程请求队列已启用；响应头 `X-AnchorRead-Instance-Id` 可用于关联具体实例。该状态不等于整个 MCP endpoint 已经无状态化：`MCP-Session-Id` 仍需 sticky routing，且文件型 pairing/OAuth store 需要共享 `/data` 卷。

## 回滚

- **自动回滚**：候选或新容器健康检查失败时，`remote-deploy.sh` 自动恢复上一版容器。
- **手动回滚到某历史提交**：用 `workflow_dispatch` 或 `-Ref` 指定历史提交对应的 ref 重新部署；镜像按 `<full-sha>` 标签长期保留在 GHCR，可直接拉取。
- 查看/清理服务器上的回滚容器与旧镜像：

  ```powershell
  ssh lcayun-1panel "docker ps -a --filter name=anchorread"
  ssh lcayun-1panel "docker images ghcr.io/xujinhuan675-cloud/anchorread"
  ```

## 故障处理

- **本地工作区不干净**：先提交或清理，不要让脚本猜测哪些文件应上线。
- **`gh` 未认证**：执行 `gh auth login`（需 `repo` + `workflow` 权限）。
- **`workflow_dispatch` 不可用**：`deploy.yml` 尚未在默认分支；改用 `-Push` 让首次部署随提交上线。
- **run 失败**：`gh run view <id> --log-failed` 查看日志；生产由自动回滚保护，旧容器继续服务。
- **服务器 `docker pull` 失败**：检查 `.env` 里的 `GHCR_USER` / `GHCR_PAT` 是否有效、服务器能否访问 `ghcr.io`。
- **SSH 连接失败**：核对 `DEPLOY_SSH_HOST/PORT/USER/KEY`，以及公钥是否已加入 `authorized_keys`。
- **域名检查失败**：先查 Cloudflare/OpenResty 转发与缓存；服务器本机检查（候选/线上端口）仍是部署是否成功的第一证据。

当前线上应用容器端口是 `127.0.0.1:3001`，不要直接暴露到公网；公网入口由现有 OpenResty 与 Cloudflare 负责。
